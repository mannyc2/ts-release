## Why this matters

The preserved prototype contains substantial native provider research but also
10,932 production lines under its publication subsystem and repeated
orchestration/application/native representations. This plan carries forward the
lawful provider evidence without carrying forward that structure.

The accepted PR21 sequence requires native release/provider foundations before
effect-build producer breadth, and effect-build producer breadth before late
MCP/OpenAI/Action work. Therefore this plan covers npm, Warehouse, GitHub,
conditional Git/catalogs, core transports, and the external-provider seam only.
Plan 008 integrates real effect-build packages; Plan 008B then completes
MCP/OpenAI/Action and emits one combined local candidate.

## Target vertical law

Each provider owner named by `SYSTEM.json` includes exactly:

```text
Intent schema/version and definition identity
operation expansion and dependency edges
prepared request/native subject correspondence
observation codec and conclusion law
dispatch codec and commitment boundary
receipt/rejection/native-result codecs
provider-specific recovery law
required host capability declarations
stable executable case IDs and scorecard facet mappings
```

It is an ordinary imported value, not a registry entry. Core never switches on
provider identity. Two configured instances share implementation while keeping
distinct Intents and operation IDs. Provider siblings do not import one another.

## Scope

In scope, using exact `SURFACE.json` and `MIGRATION.json` targets rather than
prototype `src/publication/*` paths:

- npm and Warehouse native publication;
- GitHub Release and annotated-tag/ref operations;
- conditional Git/Homebrew/Scoop catalogs;
- core HTTP/Git transport mechanics only where `SYSTEM.json` assigns them;
- packed external-provider composition and two-instance continuation;
- stable executed-case manifests and semantic local-evidence binding;
- per-wave migration deletion and marginal-cost accounting.

Out of scope:

- effect-build P/Q producer integration;
- MCP, OpenAI, first-party Action integration, and self-release convergence;
- live provider evidence or mutation;
- new packages/exports/formats/states or Effect versions;
- a generic mutation language, provider registry, optimistic replay fallback,
  credentials, publication, tags, or releases.

## Step 1: Generate executable case authority

From the Plan 005 system contract, generate a strict stable case registry and a
credential-free executed-case manifest. Each case records stable ID, provider/
operation owner, scorecard rows/facets, independent fixture/transcript IDs,
expected durable/native facts, canonical gate, and actual result digest.

A case counts only when its assertion body executes and completes. Test-file
presence, a matching name, an export, or free text is not evidence. Keep wire
transcripts/provider doubles independent from the implementation under test.

Reject invented IDs, skipped/unexecuted cases, wrong rows/facets, stale
manifests, duplicate claims, and free-text-only witnesses.

## Step 2: Prove one vertical construction grammar on distinct laws

Use npm and conditional Git as semantically different witnesses before sharing
any constructor/helper. The grammar may collect codecs, operations,
preparation, observation, dispatch, recovery, and case metadata; it may not
contain live mutable clients, credentials, Layers, hidden closures, global
registration, or a generic HTTP mutation protocol.

Prove multiple operations, per-file/asset partial progress, mutable and
immutable remote facets, core and opaque provider effects, multiple instances,
and strict native durable values.

Every extracted common law must be present in `SYSTEM.json` with both concrete
witnesses. Otherwise keep it provider-local.

## Step 3: Implement npm and Warehouse waves

For npm preserve native publication bytes, initial/later dist-tags, plural
workspaces, structural private omission, provenance/Sigstore correspondence,
OIDC authority, read-back, and no blind resend after ambiguity.

For Warehouse preserve per-file coordinates, trusted publishing, duplicate/
conflict law, partial progress, compatible index boundaries, and response-loss
honesty. Do not unify npm and Warehouse commitment/replay law.

Implement only their exact migration rows. Delete their prototype duplicate
orchestration/representations in the same wave. Bind every local D01/D02/K02
facet to executed cases while retaining honest live-open reasons.

Record gross additions, deletions, relocations, concepts/branches/edges removed,
largest modules, and cost of another workspace/file case.

## Step 4: Implement GitHub and conditional-Git/catalog waves

For GitHub preserve annotated tag/ref facts, draft/publish state, independent
asset operations, full-resource graph preflight, partial progress, response
loss, and exact release/asset bytes. Invalid complete graphs produce zero
provider effects.

For conditional Git preserve complete object-set construction, expected-old
CAS, atomic one/two-path commits, lost-response read-back, and separate
Homebrew/Scoop content and consumer law. Shared Git transport mechanics do not
merge product rendering law.

Implement exact D03-D05 migration/case rows. Measure another asset and another
catalog renderer as marginal probes.

## Step 5: Re-prove external-provider and instance independence

Pack the selected public packages into a clean consumer outside the monorepo.
Implement a provider unknown to core/CLI through ordinary imports and permitted
capabilities. Prove strict codecs, native values, core/opaque transports, two
configured instances, and process-2 continuation.

The second instance changes zero kernel/provider-package source. The external
provider changes zero kernel, host, CLI, or first-party-provider source and
requires no registry/allowlist edit.

## Step 6: Bind local evidence semantically

Generate local evidence references from stable case ID, canonical gate ID,
executed-manifest version/digest, exact source/package coordinate, and scorecard
facet. Free text may explain but cannot satisfy a facet. Local cases cannot
replace a live/hosted/credentialed oracle.

Run the launch-evidence checker and require the same closure count unless new
evidence genuinely satisfies the pre-existing authority level. No row is
closed merely because implementation moved.

## Step 7: Complete migration and compression accounting

Resolve every Plan 007 `MIGRATION.json` row. Delete duplicated provider
orchestration, schemas, operation lists, conversions, and helpers in the same
wave. File splitting, generated tables, and moved Schemas count as relocation
until a representation/branch/workflow actually disappears.

For each provider/mechanism record total product source, largest modules,
operations/branches, case coverage, package/export changes, and gross marginal
median/p90/max. Enforce Plan 005's total and marginal budgets and exact package/
import/public-surface freeze.

## STOP conditions

- A native law lacks an independent fixture or exact scorecard mapping.
- Compression weakens continuation, commitment, partial progress, byte
  correspondence, or provider-specific replay.
- A proposed shared law has one witness, or a new package/export/state is needed.
- Evidence closure depends on free text, local/live relabeling, or a skipped case.
- Migration/budget gates remain red after two measured redesign attempts.
- Work requires effect-build, MCP/OpenAI, credentials, live mutation, new scope,
  compatibility peers, or a second runtime/journal.

## Maintenance notes

Future provider changes update case/facet mappings, migration/source history,
and marginal-cost records together. Capability is proved by an executable
vertical, never by an export or table row alone.
