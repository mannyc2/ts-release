## Why this matters

A green unit suite or 69 checked rows can still coexist with duplicated
orchestration, architecture drift, unbounded source growth, a hidden fallback,
or evidence bound to a different artifact. Earlier project history contains
multiple “complete” candidates later invalidated by stronger review. The final
gate must therefore certify product outcomes and the architecture that makes
them trustworthy.

This plan proves one canonical representation, one transition/effect owner,
provider and producer vertical reachability, semantic evidence, public host
parity, source/marginal budgets, and exact artifact coordinates. It emits one
immutable certificate with explicit limitations. It makes no perfection claim
beyond those measured invariants.

## Steps

### Step 1: Freeze a complete coordinate manifest

Generate a canonical manifest of tracked source, submodules/research mirrors
used by gates, package tarballs, Action bundle, effect-build packages, tool
versions, executed-case manifest, ledger, and all live evidence records. Resolve
every locator and hash its exact bytes. Reject dirty/untracked production files,
mutable branch-only coordinates, symlinks escaping the checkout, missing hosted
records, and inconsistent source SHAs.

Verify Plan 003's v1 lineage disposition and bundle as preserved provenance,
Plan 004's effect-build terminal lineage, and the required/forbidden ancestry
from `SYSTEM.json`. The candidate must descend from PR21 and must not descend
from PR22 or the overlay evidence commit. Verify every `MIGRATION.json` row is
resolved; a certificate cannot silently choose or merge prototype histories.

**Verify:** coordinate manifest regenerates byte-for-byte and every referenced
artifact/source/record hash matches.

### Step 2: Re-prove the canonical representation and deterministic machine

Run schema golden vectors and strict decode/re-encode for bundle, plan, all
provider Intents/native facts, journal events, and report. Prove:

- one canonical encoding per durable fact;
- report/indexes are derived and never independently writable;
- exactly six journal event families unless Plan 005 explicitly versioned a new
  research-approved event;
- operation IDs are core-derived;
- no implementation provenance participates in replay authority;
- one pure transition owner and one effect interpreter;
- no provider-ID switch/allowlist or global registry;
- no compatibility reader, legacy namespace, fallback journal, or parallel
  orchestration in CLI/Action/YAML.

Run every legal/illegal transition, crash boundary, two-runner race,
correspondence mismatch, supersession-late-result, and append-ambiguity case.

**Verify:** architecture ownership scan, golden vectors, transition registry,
fault matrix, and mutation-owner scan all pass with exact expected counts.

### Step 3: Re-prove every provider and producer vertical

From clean packed installs, run all stable case IDs for ts-release providers and
the real effect-build integration. Verify each advertised capability connects:

```text
public construction -> strict Intent/facts -> machine operation -> native
provider/producer Effect -> exact fact/output -> report/evidence row
```

Reject exported-but-unreachable declarations, test-only fake paths, skipped host
cells, and a case registry entry with no executed body. Verify multiple provider
instances and third-party imports change zero kernel source.

**Verify:** every selected row has an executed implementation case and every
public capability is reachable; unsupported/deferred surfaces remain rejected.

### Step 4: Re-prove evidence and shipped-host correspondence

Recompute the canonical digest of all 69 rows and live records. For each row,
verify exact source/package/tool coordinates, required facets/levels, executed
case, output digest, public locator where applicable, and redaction. Sample no
fewer than all high-risk rows defined in Plan 009 plus a deterministic random
sample of the remainder.

Rebuild package tarballs and Action bundle reproducibly, compare exact bytes,
and rerun clean install/import/bin/Action smoke tests. Verify first-party CLI and
Action select the documented JournalStore and share the one machine.

**Verify:** both evidence gates report 69/69; package/Action rebuilds are
byte-identical or have an explicitly accepted reproducibility boundary; public
bytes match bundle/certificate digests.

### Step 5: Enforce semantic compression and marginal-cost budgets

Run the exact Plan 005 counting policy. Report:

- total production and test source by subsystem;
- generated inputs and outputs;
- top module sizes and branch points;
- durable concepts/variants and invalid-state checks;
- public exports, packages, Action inputs/outputs, orchestration owners;
- mutation call sites and credential-acquisition sites;
- exact `MIGRATION.json` disposition/deletion status;
- per-wave and per-outcome median/p90/max marginal cost.

Require every frozen hard threshold and stretch-target disposition. The initial
program requires at least 50% reduction from the preserved full-v1 prototype
production baseline;
only an explicit Plan-005 maintainer decision may have changed that target. Do
not exclude provider wire models, generators, or host source.

Growth without a new executable user outcome or stronger invariant fails. A
module split without lower ownership/state complexity does not count as
compression.

**Verify:** final budget checker exits 0 and its report regenerates byte-for-byte.

### Step 6: Conduct an independent cold review

Give a reviewer only the frozen contract, source coordinate, case/ledger
manifests, and certification commands—not the implementation narrative. Require
them to search for:

- duplicate canonical facts/owners;
- invalid states representable across type boundaries;
- fallback/compatibility growth;
- provider effects outside the interpreter;
- credential/trust leaks;
- provider-law generalization without two witnesses;
- evidence level inflation or self-referential fixtures;
- uncounted source/generator complexity;
- cross-repository Apple/journal duplication;
- shipped-host divergence.

Record findings with severity and exact disposition. Any open P0/P1 blocks the
certificate; do not patch it in this branch.

**Verify:** independent review record has zero open P0/P1 and is bound by digest
to the exact candidate/manifests.

### Step 7: Emit and validate the final certificate

Generate the strict certificate and human projection. State honestly:

- exact 69/69 scope and evidence date;
- architecture and budget results;
- exact published/self-release coordinates already produced in Plan 009;
- ten resolved-later choices, 30 named later leaves, and seven deferred
  maintained destinations;
- limitations such as provider retention, credential expiry, and facts that may
  require future reacceptance.

Add `scripts/check-research-complete-certificate.ts` and the Bun script. It must
recompute every digest/count and reject source/evidence drift, missing gates,
open review findings, secrets, or optimistic completion language.

**Verify:** all commands in “Commands you will need” pass from the final clean
SHA; the certificate checker prints the exact source SHA and 69/69 closure.

## STOP conditions

- Any predecessor plan or 69/69 closure is not genuinely terminal.
- Exact source/package/evidence coordinates cannot be frozen or reproduced.
- A canonical fact, transition, mutation, journal, or orchestration has multiple owners.
- A public capability is unreachable or a selected row lacks an executed case/oracle.
- Any hard architecture/marginal/source budget fails.
- Any evidence record is stale, mutable, secret-bearing, or at the wrong level.
- Independent review has an open P0/P1.
- Certification would require a source fix, evidence rewrite, remote mutation,
  or widened scope. Create/reopen a remediation plan instead.

## Maintenance notes

The certificate is immutable evidence for exact coordinates, not a permanent
claim about changing providers. Future source, package, journal-deployment, or
provider-law changes must identify affected traceability entries/cases and rerun
their certificate slices. A new outcome begins in the scorecard and marginal-
cost ledger before implementation.
