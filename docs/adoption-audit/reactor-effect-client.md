# reactor-effect-client adoption audit

Audited 2026-09-26. Repository: [mannyc2/reactor-effect-client](https://github.com/mannyc2/reactor-effect-client). Source snapshot: `origin/main` at [`f821a9084cf51e9aac591388db0788cb90501bf0`](https://github.com/mannyc2/reactor-effect-client/commit/f821a9084cf51e9aac591388db0788cb90501bf0), also the main SHA in the latest release runs. The checked-out `examples-redesign` branch was older and had unrelated changes; it was not modified or treated as current main.

The important findings are a confirmed ts-release large-payload failure, a recovery workflow that initially prevented installing its fix, recurring publication visibility delays that still require manual observation, and two distinct consumer integration defects around CI attempts and duplicated package metadata. These have different owners and should not all be described as kernel bugs.

## Adoption and actual usage

- **2026-09-22 23:30 UTC:** [`fc60ee2`](https://github.com/mannyc2/reactor-effect-client/commit/fc60ee290b69b64653b955c8b093721b3a621e5c) adopted ts-release **0.4.1** with a separately locked `release-tools/` application and immutable candidates. The initial private-repository integration used token authorization without provenance. The [contemporaneous qualification note](https://github.com/mannyc2/reactor-effect-client/blob/fc60ee290b69b64653b955c8b093721b3a621e5c/work/ts-release-qualification.md) explicitly distinguishes offline encoder checks from hosted publication.
- **2026-09-23 00:18 UTC:** [PR #1](https://github.com/mannyc2/reactor-effect-client/pull/1) switched the now-public repository to npm trusted publishing and retained Sigstore provenance. The package namespace was bootstrapped once using a code-free `0.0.0-reserved.0` placeholder. This was an authentication/setup change, not evidence of a ts-release failure.
- **2026-09-23 00:49 UTC:** [PR #2](https://github.com/mannyc2/reactor-effect-client/pull/2) expanded one publication into three packages sharing a version: portable `reactor-effect-client`, `reactor-effect-browser`, and `reactor-effect-native`. Both host packages depend on the client's publication because they pin it as an exact peer.
- **2026-09-23 03:23 UTC:** [PR #4](https://github.com/mannyc2/reactor-effect-client/pull/4) upgraded core/provider to **0.4.2** and pinned the Action to `fa50ce368c50e9a28a2e57f667d454374e7b209c`. These remain the release-tool versions at the audited snapshot. Its own Effect and platform runtime remain aligned at **4.0.0-rc.115**, separate from the SDK's later `^4.0.0-rc.117` package policy. [Dependency manifest](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/package.json#L11-L21).

The workflow promotes archives already built and smoke-tested in main CI. It does not build during publication. Manual `prepare` signs each archive and retains its original Bundle, Plan and content; manual `publish` requires confirmation of all three coordinates; `observe` resumes the original evidence without sending publication requests. There is one Git CAS journal per repository/version and no GitHub release or tag operation. [Workflow](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/.github/workflows/release.yml), [runbook](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/README.md).

## Findings

### REC-1 — Five releases outlasted the observation budget after successful publication acknowledgement

**Observed consumer observation-budget exhaustion while using ts-release 0.4.2.** All five runs below have a successful ts-release Action step followed by a failed `Retain fresh observations without replaying publication` step. The log ends with `Registry visibility remains unconfirmed` and exit code 2. Each was subsequently resolved by a separate **observe** run against the **same original candidate**, with no second publication dispatch.

| SDK version | Failed publish run, UTC start | Successful observe run | Package(s) still awaiting first satisfied observation at the failed run's end |
| --- | --- | --- | --- |
| 0.3.0-rc.0 | [35947070537](https://github.com/mannyc2/reactor-effect-client/actions/runs/35947070537), Sep 24 02:23:54 | [35947997264](https://github.com/mannyc2/reactor-effect-client/actions/runs/35947997264), 02:36:56 | native |
| 0.3.2 | [36078076488](https://github.com/mannyc2/reactor-effect-client/actions/runs/36078076488), Sep 25 00:33:22 | [36078487956](https://github.com/mannyc2/reactor-effect-client/actions/runs/36078487956), 00:38:47 | client, browser |
| 0.3.3 | [36095156377](https://github.com/mannyc2/reactor-effect-client/actions/runs/36095156377), Sep 25 04:36:55 | [36095478472](https://github.com/mannyc2/reactor-effect-client/actions/runs/36095478472), 04:41:48 | native |
| 0.3.4 | [36143192274](https://github.com/mannyc2/reactor-effect-client/actions/runs/36143192274), Sep 25 13:47:17 | [36143692801](https://github.com/mannyc2/reactor-effect-client/actions/runs/36143692801), 13:51:56 | client |
| 0.4.0 | [36166135316](https://github.com/mannyc2/reactor-effect-client/actions/runs/36166135316), Sep 25 17:16:59 | [36166601295](https://github.com/mannyc2/reactor-effect-client/actions/runs/36166601295), 17:21:25 | all three |

The application implements **six complete `runApplication(..., "observe")` calls separated by five-second sleeps**. That is 25 seconds of deliberate sleeping, not a 30-second total deadline: admission, native provenance verification, registry reads and Git journal work recur in each iteration. Actual reporting phases in these failed runs took about **111–150 seconds**. [Implementation, lines 29–62](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/report.mjs#L29-L62).

The 0.4.0 journal gives particularly clear evidence. npm metadata returned HTTP 200 but the expected versions were absent through 17:20:41–52 UTC. The later observe run first recorded the expected native version at 17:22:00, browser at 17:22:04, and client at 17:22:09. All eight retained version journals have exactly **three `DispatchStarted` and three `ReceiptAccepted` events** and eventually satisfied observations for all packages. The 0.4.0 evidence is preserved in [last absent client observation](https://github.com/mannyc2/reactor-effect-client/blob/e2df666efdaa9a554b403fbd2a4f6e5560ae0815/event.json), [first satisfied client observation](https://github.com/mannyc2/reactor-effect-client/blob/61180a2ad35ef42166a2f50c291e1306f215cedb/event.json), and [journal tip](https://github.com/mannyc2/reactor-effect-client/commit/662ccf3c07fa52f80d1db2c4227727e150d8843a).

**Interpretation:** the evidence supports delayed registry visibility after acknowledgement; it does not identify npm's internal propagation/cache mechanism or the exact instant the packages became visible between observations. These are not the earlier parser defect and not evidence of rejected uploads. The conservative report is correct to avoid claiming visibility prematurely, but its fixed budget repeatedly turns otherwise accepted releases red and makes operators launch recovery manually. Five of the seven post-upgrade first-publication runs needed this extra observe run; 0.3.0 and 0.3.1 finished within their first run's budget.

**Improvement:** make `AcceptedAwaitingVisibility` a clear report state; offer a configurable elapsed-time observation policy and observation-only continuation with the original candidate/journal. Show each package's acknowledgement and last real observation separately. Preserve nonzero/incomplete status where desired without recommending republishing. Reuse admitted immutable data within a bounded observation session rather than reopening the entire application for each poll.

### REC-2 — Large native publication passed preparation but failed HTTP request admission

**Confirmed ts-release defect, fixed upstream and adopted locally.** The first 0.2.0 publish [run 35806217606](https://github.com/mannyc2/reactor-effect-client/actions/runs/35806217606), Sep 23 01:25 UTC, failed with `http-request-owner: HTTP authority or wire value could not be admitted`. [PR #4](https://github.com/mannyc2/reactor-effect-client/pull/4) identifies the cause as a large-JSON parser failure before native transport dispatch after the client had already published. The native request was **18,235,775 bytes**.

The original candidate was successfully prepared by [run 35804115261](https://github.com/mannyc2/reactor-effect-client/actions/runs/35804115261) using 0.4.1. The consumer already exercised every publication through the provider's real encoder during preparation, so encoder success did not cover the later HTTP owner/parser path. [Preparation loop](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/prepare.mjs#L198-L206).

**Resolution:** ts-release 0.4.2 plus consumer PR #4. Its recorded validation used Node 24.15.0 and native Sigstore verification against the original candidate: all 11 retained files stayed unchanged and all three request hashes matched the original journal evidence. The repaired [publish run 35814156712](https://github.com/mannyc2/reactor-effect-client/actions/runs/35814156712) succeeded at 03:23 UTC without preparing a replacement. The upstream repair is [ts-release PR #43](https://github.com/mannyc2/ts-release/pull/43).

**Improvement:** preparation should offer a complete zero-dispatch request-admission check that covers the transport-owned wire format, not only provider encoding. Maintain realistic native-package payload regressions on supported Node and Bun runtimes, including long JSON strings and base64 expansion. Distinguish an admission/parser error from authorization failure in diagnostics; the original action message pointed broadly at dependencies, input and journal access.

### REC-3 — Restoring the original application commit prevented recovery with repaired dependencies

**Confirmed consumer recovery-design failure, exposed by REC-2.** The original workflow checked out the candidate's preparation application commit. That restored the same 0.4.1 lockfile on every retry, so a tooling fix merged to main could not be used while retaining the candidate. This was a separate obstruction from the parser itself. [PR #4 rationale and changes](https://github.com/mannyc2/reactor-effect-client/pull/4), [fix commit 891480d](https://github.com/mannyc2/reactor-effect-client/commit/891480d8e422d55a4b75109f069506bb77be75e1).

**Resolution:** candidate `applicationCommit` remains the original preparation/source identity; separate invocation-only `executionHostCommit` identifies the exact current manually dispatched main checkout. Both original workflow runs/attempts and current checkout are validated. The host may install fixed dependencies while Bundle, Plan, signed provenance, archives, journal and request identities stay unchanged. Current admission still grants no automatic replay or risk acceptance. [Host checks](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/host.mjs#L5-L25), [input schema](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/model.mjs#L106-L125).

**Improvement:** provide a supported execution-host upgrade contract and compatibility check that compares retained request hashes before recovery. Candidate source identity and executor identity should be separate concepts in examples, APIs and action output from the start.

### REC-4 — Neither kind of CI rerun could originally produce an eligible replacement artifact

**Confirmed by workflow-consistency review; no specific failed hosted rerun was established in this audit.** [PR #3](https://github.com/mannyc2/reactor-effect-client/pull/3), merged Sep 23 00:59 UTC, documents two separate failure paths:

1. **Re-run failed jobs:** the successful package job is not rerun, so its retained qualification has the old attempt while the workflow API reports a newer `run_attempt`. Preparation rejects the mismatch.
2. **Re-run all jobs:** uploads reused immutable artifact names within the run and failed instead of replacing them. Both `native-<platform>` and `npm-package` uploads needed `overwrite: true`.

**Resolution:** [`e11b4e3`](https://github.com/mannyc2/reactor-effect-client/commit/e11b4e37ee4bc422fd2d9e38965b1b9489ebe41e) added overwrite and documented full rerun/new-main-commit as the supported route. A failed-jobs-only rerun remains intentionally ineligible. Staging was also narrowed from all `*.tgz` files to the archives named by `package-identity.json`; the PR explicitly calls that hygiene because preparation already consumed only named archives. [Current uploads/staging](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/.github/workflows/ci.yml#L271-L357).

**Improvement:** supply a tested GitHub artifact qualification recipe covering run attempts, full reruns, retained successful jobs, replacement semantics and artifact IDs/digests. Explain exactly which producer attempt qualified bytes, rather than exposing only a generic identity mismatch. Do not casually relax attempt validation to make retries pass.

### REC-5 — A copied Effect policy constant blocked release qualification after an SDK dependency update

**Observed consumer implementation defect; fixed.** [PR #27](https://github.com/mannyc2/reactor-effect-client/pull/27) widened the SDK catalog to `^4.0.0-rc.117` for 0.3.3. The pack smoke produced that string in `package-identity.json`, but `release-tools/model.mjs` still required exactly `4.0.0-rc.115` using `Schema.Literal(effectPin)`.

Main CI [run 36093131674, attempt 2](https://github.com/mannyc2/reactor-effect-client/actions/runs/36093131674/attempts/2) passed native/runtime checks and packed all three 0.3.3 archives, then failed `Bind qualified archives to this main CI run` at 04:16:59 UTC with `SchemaError: Expected "4.0.0-rc.115" at ["effect"]`. [Job log](https://github.com/mannyc2/reactor-effect-client/actions/runs/36093131674/job/107941547830).

**Resolution:** [PR #28](https://github.com/mannyc2/reactor-effect-client/pull/28), merged Sep 25 04:29 UTC at `8b3fa77f857ccb9c6140e9fd9beb4b25c9683499`, changed two duplicated values in model and test fixture. The release tools' own Effect runtime stayed rc.115. Successful preparation [36095069573](https://github.com/mannyc2/reactor-effect-client/actions/runs/36095069573) followed; publication then encountered REC-1 before observation succeeded.

**Improvement:** separate declared consumer-package policy from the release engine's runtime dependencies and derive the former from one reviewed manifest/catalog source. Add a zero-network qualification check using actual packed identity data in PR CI. The production stamp runs only on main, while fixtures duplicated the same stale constant, so offline release tests could pass without detecting the drift. [Literal schema](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/model.mjs#L93-L104), [main-only stamp](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/.github/workflows/ci.yml#L327-L336).

## Current review risk: repaired hosts still need historical candidate compatibility

This is a **code-review finding, not a newly reproduced failed release**. Splitting execution host from candidate source does not by itself make every later host able to admit every older candidate.

Current `loadCandidate` revalidates retained `package-identity.json` using the current model, which requires `effect: "^4.0.0-rc.117"`, ABI 4, and the newer native SBOM identity field. The original 0.2.0 recovery host admitted rc.115 and ABI 2. Therefore the current schema cannot admit that old identity unchanged, even though the candidate's own format identifier remains `reactor-ts-release/v3`. This also affects older rc.115 candidates before the Effect policy change. [Current validation call](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/application.mjs#L92-L108), [current model](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/model.mjs#L72-L107), [original recovery model](https://github.com/mannyc2/reactor-effect-client/blob/891480d8e422d55a4b75109f069506bb77be75e1/release-tools/model.mjs#L70-L104).

All eight observed releases are complete, so this has not been shown to strand an unresolved candidate today. It motivates versioned candidate-policy decoders, retained policy identifiers and a compatibility corpus spanning actual prior releases. Historical admission must preserve the original policy without silently weakening today's new-candidate requirements.

## Integration patterns worth bringing into ts-release

| Existing consumer pattern | What ts-release could provide |
| --- | --- |
| Nine production `.mjs` files, **1,127 lines**, plus five test/fixture `.mjs` files, **2,090 lines**, and a **197-line release workflow** at the audited commit. This includes real package/native policy as well as reusable release plumbing. | A composable reference application or helper layer for candidate directories, CI selection, run identity validation, confirmation, Git journal credentials and report persistence. Preserve application ownership of export maps, ABI/SBOM policy and qualification rules. |
| One qualified package set, same version, portable/native separation, source tree and per-file hashes, and original archive bytes through publication. | A generic qualified-artifact manifest with extensible consumer validation. Avoid forcing downstreams to duplicate qualification, package inventory and candidate persistence machinery. [Model](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/model.mjs#L51-L104). |
| Publication DAG: client first; browser and native each depend on client, with no ordering edge between the two host packages. Their actual sibling order may vary by operation IDs. | A workspace plan helper deriving exact-peer edges. Clearly distinguish dependency acknowledgement from registry visibility: the current core gates on `Satisfied`, which accepted receipts can establish, while this consumer separately requires fresh observations for final visibility. [Plan construction](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/prepare.mjs#L150-L188), [dependency/recovery tests](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/test/Recovery.test.mjs#L175-L235). |
| All package namespaces and trusted-publisher bindings must exist before the first real release; otherwise a host's credential exchange can fail after the client publishes. | An explicit optional preflight/doctor for package existence and trust prerequisites, authorized separately from publication. Treat this as a documented partial-release hazard, not a proven incident in this repository. [Setup runbook](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/README.md#L24-L47). |
| Each archive gets retained Sigstore provenance; trust roots are extracted from pinned `@sigstore/tuf` seed data in consumer code. | A supported trust bootstrap helper and simpler provenance wiring that retain exact source verification. [Consumer trust code](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/provenance.mjs#L51-L84). |
| All reports/candidates live as Actions artifacts for 90 days; journal branches survive independently. | Candidate export/archive support and a recovery-readiness report that checks the complete retained bytes before artifact expiry. A durable journal alone is insufficient to recover expired content. [Retention guidance](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/release-tools/README.md#L155-L182). |

The package-specific and Effect/native-runtime requirements are useful application policy. The opportunity is to make shared release mechanisms easier to reuse and validate, rather than relocating every consumer rule into the kernel.

## Evidence coverage and limitations

- Read adoption/fix history, relevant PR bodies and available discussions, current release sources/tests, and all eight locally fetched journal histories: 0.2.0, 0.3.0-rc.0, 0.3.0, 0.3.1, 0.3.2, 0.3.3, 0.3.4 and 0.4.0.
- Queried both pages of GitHub's workflow-run collection: **116 runs total; 22 release runs, six failures**. All six failed release-job logs were inspected, as were the six corresponding successful recovery jobs and the failed 0.3.3 qualification job. One failure is REC-2/REC-3; five are REC-1. Do not count prepare runs as successful publications.
- The review-discovered rerun defect and the current historical-schema risk are explicitly separated from observed hosted failures. Namespace bootstrap and artifact-expiration concerns are documented constraints, not invented incidents.
- No new publication, workflow rerun, journal mutation, repository change, or remote issue/comment was made. This was a history/code/log audit; existing CI evidence is cited rather than claiming tests were rerun. Exact npm internal visibility timing and the full original candidate archive were not independently reconstructed during this audit.
