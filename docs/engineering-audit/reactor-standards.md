# Reactor engineering standards audit

> Historical peer-standards snapshot, captured on 2026-09-26 at the revisions below. Normative clauses and observed enforcement are evidence for the plan, not claims that ts-release has adopted every requirement. See [current implementation status](implementation-status.md) for the bounded milestone, actual verification and remaining work. These are task research documents, excluded from published packages.

Audited 2026-09-26. This replaces the earlier report's treatment of Reactor as a selection of useful Effect patterns with a requirements audit. Reactor's standard is a combination of ownership rules, a prescribed architecture review, strict compiler/linter enforcement, unusually selective testing, and proof through actual package consumers. A few scoped-resource fixes and a green test count do not establish adoption of that standard.

## Exceptions and corrections to the prior report

1. **The prior review did not follow the local audit contract.** It reported selected patterns, but omitted inventory rows with owner/contract/construction/production/consumers/boundary/tests/verdict, capability classifications, deletion tests, and complete unsafe-boundary accounting. REC-S03–S08 are requirements for the next ts-release architecture audit.
2. **Compiler and lint enforcement was materially underweighted.** The earlier report called custom compiler patching an implementation choice. The exact product is indeed a choice for ts-release, but equivalent enforced strictness and a verified compiler identity are not satisfied by a prose preference for Effect.fn. REC-S25–S29 need an explicit adopt/equivalence/defer decision and functioning gates.
3. **Testing guidance was incompletely researched.** The local selection, failure-first and evidence rules were not extracted. Test count is not a success criterion. Existing added tests cannot acquire invented historical red-green evidence; inspect their value and use direct workflow verification where required. Do not automatically delete high-risk recovery tests merely because provenance is missing.
4. **Main and local timing rules differ.** Main CONTRIBUTING:86 mandates TestClock for Effect time. Older local `eventually` polls `performance.now()` and `setTimeout(1)` ([test-kit:57](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/packages/test-kit/src/index.ts#L57)); local heartbeat tracing relies on it. This is not a recommended scheduling-test pattern. Main has a newer clock harness; the prior report's caveat about optional custom harnesses should not obscure the deterministic-time requirement.
5. **Harness support is not universal call-site compliance.** Local `Spans.test.ts:133,154` passes runner signal into finally cleanup despite CONTRIBUTING's prohibition. This is an observed static mismatch; no canceled-test leak was reproduced during this audit.
6. **Effect.fn counts were scoped too narrowly for an architectural template.** The core client/browser/native libraries do largely wrap `Effect.gen`, but first-party examples use `Effect.fn`, concrete service layers and real application composition ([Rundown:71](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/packages/client/examples/src/Rundown.ts#L71), [Programme:54](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/examples/livestream/src/Programme.ts#L54), [Ledger:37](https://github.com/mannyc2/reactor-effect-client/blob/f821a9084cf51e9aac591388db0788cb90501bf0/examples/livestream/src/Ledger.ts#L37)). These application examples are directly relevant to ts-release's CLI/workflow ownership.
7. **Defect preservation has a real exception.** Session supervision catches an entire Cause and converts unrecognized failures into Protocol with original cause in detail ([session.ts:456](https://github.com/mannyc2/reactor-effect-client/blob/b7e7448ae40af80b80258e1b638bf0277bdd1c65/packages/client/src/session.ts#L456)). Preserve the finding as a specialized reporting policy, not a general endorsed error adapter.
8. **The skills themselves contain transplant drift.** Testing's E2E reference names `docs/TOOLCHAIN.md` and `vp run ready`; Reactor has no such command authority. Test-design mentions `@effect-agent/testing`. Use Reactor CONTRIBUTING/verify as local authority and translate these references before adopting policy. The AGENTS path override correctly handles Bun's isolated Effect installation.
9. **Narrative version claims can be stale.** Local CONTRIBUTING:147 says ts-release 0.4.1, whereas release-tools README:10–16 and its manifest/workflow identify 0.4.2. Main's shared-platform prose likewise needs comparison with current manifest/lock. Do not select versions from a narrative paragraph.

## Required planning outputs before more ts-release implementation

The next plan should map REC-S01–S50 to concrete current ts-release evidence and a disposition, rather than declare wholesale adoption. At minimum:

1. Complete the service/capability/unsafe-boundary inventory, including CLI, Action, provider packages, persistence, preparation, journal recovery, subprocesses and current test substitutes. Trace the actual end-to-end prepare/publish/observe/resume operations.
2. Record explicit keep/remove/merge/relocate decisions and target module owners. Preserve immutable candidate identity, journal replay semantics, public error compatibility, request hashes, approval and visibility rules.

4. Audit existing and proposed tests by concrete costly failure and strongest sufficient seam. Reuse installed CLI/Action/recovery workflows and saved receipts. Any future necessary isolated test starts with an actual failure inventory and meaningful red; no quota or retrospective process claim.
5. Make each implementation slice carry requirement IDs, exact files, dependency/ownership change, compatibility effect, cheapest proof, final gate and remaining limitation. Public contracts are qualified from packaged consumers on the actual supported runtime.
