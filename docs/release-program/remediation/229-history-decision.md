## Decision

The installed npm and GitHub publication profiles use
`historyRequirement: "optional-evidence"`. Their exact remote observations,
together with the verified prepared bundle, reconstruct the safe next action.
No correctness-critical `ReleaseHistory` service or mutation journal is added.
Losing local history must not block a fresh exact observation, and retaining a
journal must never authorize mutation replay.

This kernel conclusion is limited to npm and GitHub. Plan 230 subsequently
installed a PyPI profile with `historyRequirement: "durable-cas-required"`;
its mutation path implements the future-adapter rule below and fails closed
unless the host supplies a shared terminal claim store. Catalog modules remain
uninstalled. No automated correction adapter is admitted: npm deprecation and
GitHub release amendment remain operator proposals, and PyPI yanking remains
observation-only.

## Outcome-unknown rule

A mutation whose dispatch may have begun is never made safe merely by logging
it. For the current observable providers, the coordinator can advance only
after a new conclusive provider observation. If observations exhaust, the
release remains `UncertainSubject`; a new runner must observe again and must not
blindly replay the mutation.

If a future admitted adapter performs a mutation that cannot be reconstructed
by exact remote observation, its profile must change to
`durable-cas-required` before dispatch is reachable. That requirement means a
shared durable compare-and-set claim store spanning all runners. A local
append-only file, process lock, CI workspace, or ephemeral cache is
insufficient because another runner cannot atomically observe and claim the
same dispatch right.

For such a future adapter, the state transition is one-way:

1. atomically claim the exact prepared subject before dispatch;
2. once dispatch may have started, record the claim as terminal
   `OutcomeUnknown` if no conclusive result is available;
3. never let lease expiry, timeout, runner death, lock loss, or a new claimant
   turn `OutcomeUnknown` into `Absent` or retry permission;
4. advance only from new conclusive provider evidence or an explicit typed
   operator decision.

An operator decision is a new canonical fact about what to do next. It is not
proof of the original provider outcome and must be reported separately from
provider observation.

## Journal boundary

Optional audit evidence may record sanitized observations, dispatch-start,
provider result, final observation, and typed operator decisions. It earns no
authority:

- graph and prepared bytes remain authoritative only through the canonical
  prepared bundle;
- journal loss does not change a safe next action for an installed observable
  provider;
- journal presence never proves remote equivalence, absence, or exactly-once
  execution;
- a journal must not carry graph bytes as an alternate authority;
- no event, lease, timeout, or runner identity permits blind replay.

The kernel npm/GitHub profiles still need no history service because their
fault cases recover from provider truth or stop uncertain. Plan 230's PyPI
profile is the first installed `durable-cas-required` module: coordinator
construction requires its claim boundary, the claim executes before mutation
credential acquisition, and unavailable or occupied claims block dispatch.
The host contract requires a terminal store shared by every runner; the stock
CLI and Action provide none and therefore cannot dispatch PyPI token uploads.
Protocol tests carry one shared store across fresh subject graphs and prove a
lost response cannot produce a second POST. A process-memory test double is
evidence for the seam and transition only, never a production durability
claim.
