# Implementation Plans

Generated by the improve skill on 2026-06-29, with hard-cutover LOC-reduction
plans added on 2026-06-30, release-shipment plan 113 added on 2026-07-03, and
the 0.1 GoReleaser-shaped pipeline wave (114-118) added on 2026-07-03.
Execute in the order below unless dependencies say otherwise. Each executor
should read the plan fully before starting, honor its STOP conditions, and
update the status row when done.

The 113 → 114 → 119 → 115 → 116 → 117 → 118 sequence is the current priority path
toward 0.1.0: ship the already-merged hard cutover as 0.0.8, design the
pipeline architecture and 0.1 public API contract, build the kernel, port
every surface to pipes (proving extension cost with new checksum/archive
features), expose the public TypeScript API with the CLI/Action as thin
wrappers, then run the Effect polish sweep. Primary metric: lower LOC via
architecture, never code golf. Publish operations remain data until the
operator explicitly dispatches them.

The 108-111 sequence is the new priority path. These plans intentionally make
breaking cuts with no legacy aliases, fallback config parser, or compatibility
export map. Older incremental plans remain in the repository for history, but
do not execute an older plan when it conflicts with 108-111.

  implements the first Builder against this contract so it is never
  retrofitted.

## Findings considered and rejected

- Delete execution approvals entirely: rejected because `SPEC.md` and
  `ARCHITECTURE.md` correctly require explicit approval before externally
  visible publication. The issue is framing, not the existence of publish gates.
- Add every package manager immediately: rejected because the current model
  should prove npm, GitHub Releases, Homebrew, Scoop, and PyPI first. New
  adapters should be added end to end only when they carry real ecosystem
  differences.
- Create a standalone Effect GitHub API repository before fixing this repo:
  rejected for now because there is only one concrete consumer and the API shape
  should prove itself internally before becoming a package boundary.
- Add Octokit as the GitHub Releases live path: rejected for this plan because
  it would still need Effect service, typed error, schema, and evidence wrapping
  while adding a dependency tree to the core package.
- Keep compatibility aliases for removed commands or config fields: rejected
  because the current direction is a hard cutover to reduce LOC first.
- Keep the old `_tag` target config parser while introducing compact config:
  rejected because dual schemas preserve the overbuilt model and double the
  test matrix.
- Remove the `render` CLI command to match the plan-112 six-command contract
  exactly: rejected for now because the self-release catalog step
  (`release:catalogs`) depends on it. Record it as an accepted deviation and
  revisit only in a deliberate contract revision.
- Implement TypeScript config loading (`ts-release.config.ts`) before shipping
  0.0.8: rejected because the unpublished cutover is the larger gap; executable
  config loading raises sandboxing and Action-runtime questions that deserve
  their own plan against a released baseline.
- Point-fix simplification sweep before the pipeline restructure: rejected —
  the 2026-07-03 audit sized standalone fixes at only ~250-350 LOC while the
  restructure (115-117) deletes the structures those fixes would polish;
  simplification folds into the restructure, with plan 118 as the residual.
- Dynamic pipe registration / plugin discovery in 0.1: rejected — a static
  ordered array in one file is the GoReleaser-proven shape; a plugin system
  is a post-0.1 direction question with no current second consumer.
- Expose an Effect-native public API in 0.1: rejected while Effect 4 is beta —
  Effect types in the public surface would make every Effect bump breaking
  for users; the Promise layer wraps the Effect engine instead (revisit when
  Effect 4 stabilizes).
- Copy GoReleaser's execute-as-you-go pipe semantics: rejected — pipes plan,
  the risk-gated executor executes; operations-as-data + explicit approval is
  this product's core safety differentiator (and enables split/merge-style
  features via ReleaseState serializability).
