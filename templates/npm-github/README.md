# npm and GitHub release application

This starter prepares immutable npm archives and a GitHub release, then publishes
through the public ts-release providers, native HTTP transport and shared Git
journal. It is the same application used by this repository. `release/*.js` and
`input.ts` are generated by `bun run build:delivery`; edit the corresponding
source in `apps/self-release/src` and `scripts/release-input.ts` when contributing.

The starter targets **0.4.1**. Until that version is published, install the
matching core, npm and GitHub archives from the reviewed candidate instead of
resolving its package.json from npm. Use Node 24.15.0 for execution, and Bun 1.3.14
for dependency installation and preparation scripts. Native provenance requires
Node; token publication also works on Bun.

If an operator explicitly supersedes a candidate before any dispatch, set
`TS_RELEASE_SUPERSEDED_CANDIDATES` to a JSON array of retained candidate directories
when generating the successor's input. The application keeps the same journal
and rejects historical Plans without a supersession record or with any dispatch.
Retain the original Bundles, Plans, content and bindings for every continuation.

## Prepare once

Copy this directory into your project's `release-tools/` directory and install
its dependencies with `bun install`. Build your project, then pack each public
package with `bun pm pack --ignore-scripts --filename <absolute-archive-path>`.
Keep the source commit, build inputs and archives available for review.

Copy `prepare-input.example.json` to `prepare-input.json`. Set the repository,
version, archive paths and release notes. Set `source.commit` and `source.tree`
to `git rev-parse HEAD` and `git rev-parse HEAD^{tree}` from the source checkout.
Each archive's real package metadata must match the selected version. A
`corePackage` field can name a package that must wait for all other npm packages.
Additional GitHub files use `assets: [{ file, publicName, mediaType }]`.

```sh
bun run prepare:release prepare-input.json
```

This retains `candidate/bundle.json`, `plan.json`, `identity.json` and immutable
`content/`. It never publishes packages or releases. A destination directory must
be new. Keep the complete candidate; recreating it is not a recovery operation.
GitHub receives the package archives, source identity, notes and extra assets.

## Observe and publish

Set `TS_RELEASE_JOURNAL_REMOTE` to the selected repository's HTTPS Git URL, for
example `https://github.com/your-org/your-repository.git`. Set `GH_TOKEN` through
your secret manager to a credential with repository contents write access; it
also authenticates the durable journal. For token publication, supply `NPM_TOKEN`
through your secret manager with the intended package publish access.

```sh
bun run input:release candidate release-input.json Token --execute
bun run observe:release release-input.json
bun run publish:release release-input.json > release-report.json
bun run verify:release release-input.json
```

`--execute` in the input command records your explicit authorization. Omit it to
create input that cannot publish. Observe mode never dispatches publication,
even with authorized input; it records observations in the shared journal. Exit
code 2 means incomplete progress, which is expected before first publication.
The verifier repeats only observations, allowing delayed registry visibility.

To use an interactive local npm login, run `npm login`, select the npm user config
explicitly with `NPM_CONFIG_USERCONFIG`, and use `Local` instead of `Token` when
creating input. The runner prints fresh npm browser challenges on stderr. Login
tokens, challenge URLs and one-time passwords are never stored in the candidate
or journal. An accepted authentication rejection is journaled before another
publication attempt is allowed. Uncertain writes remain subject to recovery.

The journal identity is stable for the repository and release version. A new
candidate with different notes, artifacts or provenance cannot quietly replace
an existing journaled Plan. To resume, rerun the original input and candidate;
only its local journal cache may be replaced. Do not delete the remote journal
or fabricate another version to bypass an unresolved outcome.

## Hosted OIDC and the Action

Configure npm trusted publishing for each existing package and your workflow.
Prepare provenance on an approved GitHub-hosted Node runner with `id-token: write`.
The preparation schema accepts `npm.authorization` as `TrustedAuthorization` and
`npm.provenance` containing `authorize: true`, the exact `ProvenanceSource`, and
explicit Sigstore trust paths. Retain that final candidate before publication.
Use `Trusted` when generating runtime input. It selects the hosted identity
exchange instead of a long-lived npm token; GitHub still uses `GH_TOKEN`.

Before publication, `node check-credentials.mjs release/application.js release-input.json`
checks the retained npm requests and trusted-publisher credentials without
publishing or appending to the journal. Diagnostics contain protocol stages and
response shape, never tokens or raw credential responses.

The repository's [release workflow](../../.github/workflows/release.yml) shows the
complete preparation, attestation, retained-artifact and publication jobs. It
installs the exact retained packages before invoking the Action launcher under
the pinned, qualified Node runtime. For your own
workflow, pin the Action to a reviewed commit, set `application` to
`release-tools/release/application.js`, and pass the complete input JSON to the
Action's `input` field. The input helper emits `application-input` to
`GITHUB_OUTPUT` when run as an Actions step. Set `observe: 'false'` only after
approval; the input's `authorize` must also be true.

Token and Trusted authorization are part of the retained Plan. Choose the mode
before publication; switching modes is not a way to resume an unfinished release.
Run native provenance under qualified Node and retain the original signed bytes
when retrying a failed publication job.
